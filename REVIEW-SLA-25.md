# SLA-25 review: CHANGES REQUIRED

Reviewed `main...integ/sla-24` at `fea9635b2e0285e18a256567b6b83026921566c4` on 2026-11-09. Do not fast-forward main to this revision. Findings below refer to files and lines at that revision.

1. **Blocker — feature modules cannot resolve PrismaService.** `apps/api/src/modules/audit-log/audit-log.module.ts:4` provides AuditLogService without importing a module exporting its PrismaService dependency. The same module visibility problem affects BusinessService, the auth providers and InterventionRepository. Providing PrismaService in AppModule does not expose it to imported modules. A Nest testing-module compile with `imports: [BusinessModule]` reproduces `Nest can't resolve dependencies of the AuditLogService ... PrismaService ... AuditLogModule`. Add an exported database provider module and import it everywhere needed (or import a global database module once), then compile the real AppModule with external clients overridden and exercise startup. This is independent of the accepted missing session middleware.

2. **Major — valid reset and invitation tokens cannot be looked up.** `apps/api/src/modules/auth/auth.service.ts:216` and `apps/api/src/modules/members/accept-invitation.service.ts:20` call `argon2.hash(token)` again and search for equality with the stored salted hash. Each hash has a new salt, so a token from the issued email fails lookup. Use a deterministic cryptographic digest consistently at issuance and lookup for these high-entropy random tokens, or use a separate lookup identifier and `argon2.verify` against the stored hash. Preserve expiry and atomic single-use consumption. Add issue/redeem/replay/expired tests for both flows. A probe confirms two hashes differ while `argon2.verify(firstHash, originalToken)` succeeds.

3. **Major — session issuance discards the credential and exposes its database representation.** `apps/api/src/modules/auth/create-session.service.ts:23` returns only tokenHash; `apps/api/src/modules/auth/auth.service.ts:84` and `:113` use that stored hash as accessToken. The generated raw token is lost. Normal hash verification cannot validate the returned credential against the stored hash; treating the stored hash itself as the bearer credential defeats storage hashing. Return the raw token once from the issuer, retain only its digest in the database, and deliver it through the architecture's session cookie when session transport is implemented. Test that the returned credential verifies against storage and differs from the stored value. This finding concerns issuance, not a demand to implement the explicitly deferred verification middleware in this change.

4. **Major — technician authorization permits reading other assignees' interventions.** `apps/api/src/modules/intervention/intervention.controller.ts:50`, `:81`, `:90` include TECHNICIAN, but generic list/today/detail calls only constrain businessId. A technician can omit/change technicianId or request another intervention ID and receive other technicians' customer data, internal notes and timeline. Architecture section 8 restricts technicians to their own interventions. Restrict generic routes to OWNER/DISPATCHER, or resolve and enforce the caller's technician membership on every read; never trust a technician-supplied assignee filter. Add tests with two technicians in one business against all three routes. Current missing middleware masks this policy defect until authenticated requests exist; a controller/metadata probe demonstrates it with a trusted technician principal.

5. **Major — solo owners cannot perform technician actions.** `apps/api/src/modules/intervention/intervention.controller.ts:211` (and every other `/tech/interventions` route) only permits role TECHNICIAN. Architecture section 2 explicitly supports OWNER memberships with isTechnician=true. Those owners can be assigned but RolesGuard rejects their reads/status actions before the service's membership/assignment checks. Permit eligible OWNER memberships (and any other role deliberately supported through isTechnician), while retaining requireTechnicianMembership and requireAssigned. Test an assigned solo owner, an owner without technician eligibility, and an unassigned caller. The current RolesGuard rejection for OWNER + isTechnician=true was reproduced.

6. **Major — rotating links does not guarantee revocation under concurrency.** `apps/api/src/modules/intervention/intervention.repository.ts:164` performs updateMany then create in a default-isolation transaction. There is no parent-row lock or uniqueness constraint on an active link per intervention. Two concurrent regenerations after revocation (zero active links) can both update zero rows and both insert active links. A later rotation therefore need not revoke the other newly issued URL. Serialize all issuance/revocation for an intervention, e.g. lock its parent row in each transaction, or use serializable isolation with conflict retry and a partial unique active-link index. Add a PostgreSQL integration test for two concurrent regenerations with and without a pre-existing active link, and rotation versus revoke. A controlled repository interleaving reproduces both inserts; this was not a live PostgreSQL test.

7. **Major — business mutations lack owner authorization.** `apps/api/src/modules/business/business.controller.ts:43` and `:51` have only ApiCookieAuth documentation, with no access or role guards, and BusinessService does not check the actor's membership role. Once an upstream principal exists, any technician/dispatcher can change branding/profile or upload a logo using their activeBusinessId. Without a principal these routes throw instead of failing closed with 401. Add AccessTokenGuard and owner authorization to mutations (and explicit authenticated access to reads), deriving the tenant from the verified principal. Test anonymous 401, non-owner 403 and owner success. The absent session middleware is accepted; omitted route authorization is a separate defect established by inspection.
